# 生成项目简报的提示词

在项目目录里对**写手 agent** 说下面这段。

不要让评审方写 —— 它写的简报带着它自己的理解偏差，下一轮它再读自己写的，会形成自我确认的闭环。

---

```
生成 docs/reviewer-brief.md，供评审 agent 每轮开头阅读，目的是让它不必每次
从零爬全仓库。

第一行必须是：<!-- verified at: <当前完整 HEAD sha> -->

按这几节写，总长控制在 150 行以内：

## 这是什么
一两句话说清项目干什么。

## 核心路径
列出改动到就必须走评审的目录/文件，每条附一句为什么它是核心。

## 架构与数据流
状态存在哪、如何变更、组件间怎么传递。只写读代码不易一眼看出的部分，
不要罗列目录树。

## 不变量
每条写成「必须 X，因为 Y」。把过往修复背后的规则写进来。

## 已知取舍
故意没做的抽象、选了 A 没选 B 的原因。

## 已知缺陷
从 docs/review-backlog.md 摘过来，一条一行。

## 测试
测试在哪、怎么跑、哪些覆盖了核心路径。确定性检查（lint / typecheck）的命令。

要求：
- 只写你能从代码和 git 历史确认的事实，不要推测
- 不确定的写进「## 待补充」，由人来填
- 不要复制大段代码
```

---

## 生成之后

**你亲自过一遍「不变量」那节。** 其余部分机械生成没问题，但不变量是这份文件的价值所在，写手可能写不全或写错。

然后提交。

## 维护规则

**改架构时更新头部那行 sha。** rubric 让评审方只读该 sha 之后的增量，sha 不更新它就会带着旧前提自信推理。

rubric 里那条「增量超 50 个提交就报 finding」是自动提醒 —— 它会主动告诉你简报该更新了。

## 为什么这份文件重要

不写的话，评审方每轮从零爬全仓库。实测中这是评审耗时的主因，成本可能超过实施本身。
